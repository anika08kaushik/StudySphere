# StudySphere — Requirements & Development Guide

StudySphere is an AI-Powered Collaborative Study Platform designed to provide students with a centralized workspace for studying, collaborating, managing projects, sharing resources, communicating, and improving productivity.

This document is the main development and setup guide for the StudySphere team.

It contains:

- Development requirements
- Local setup instructions
- Environment configuration
- MongoDB setup
- Project architecture
- Feature ownership
- API conventions
- Socket.io conventions
- Database conventions
- Git workflow
- Security rules
- Development checklist

6. Environment Variables

StudySphere uses separate environment files for the frontend and backend.

Environment files contain local configuration and sensitive credentials.

IMPORTANT

Never commit:

.env
.env.local

to GitHub.

The repository contains .env.example files showing the required variables.

7. Frontend Environment

Create:

frontend/.env

Add:

VITE_API_URL=http://localhost:5000/api

This tells the React application where the StudySphere backend API is running.

8. Backend Environment

Create:

backend/.env

Add:

PORT=5000

MONGO_URI=YOUR_MONGODB_CONNECTION_STRING

JWT_SECRET=YOUR_LOCAL_JWT_SECRET

CLIENT_URL=http://localhost:5173

Ask the project owner/team lead for the development MongoDB access details.

Never commit the actual values to GitHub.

9. MongoDB Atlas Setup

StudySphere uses MongoDB Atlas as the development database.

Development database:

studysphere-dev

The backend connects to MongoDB using:

MONGO_URI

inside:

backend/.env

Example structure:

MONGO_URI=mongodb+srv://USERNAME:PASSWORD@CLUSTER.mongodb.net/studysphere-dev

The actual credentials must remain private.

Do NOT put MongoDB credentials in:

GitHub
README.md
REQUIREMENTS.md
.env.example
Source code
Screenshots
Public documentation

# 22. Ownership Rules

Each member owns their assigned module.

Do NOT rebuild another member's module without discussing it with them.

Shared infrastructure should only be changed when necessary and should be discussed with the team.

Shared infrastructure includes:

- Authentication
- MongoDB connection
- API conventions
- Socket.io connection
- Environment configuration
- Common utilities
- Shared models
- Shared components

If a shared change is required, inform the other team members before modifying it.

# 23. API Convention

All backend APIs should follow:

```text
/api/<resource>

Examples:

/api/auth
/api/users
/api/groups
/api/memberships
/api/tasks
/api/messages
/api/documents
/api/focus
/api/notifications
/api/activity

Use standard HTTP methods:

GET     → Retrieve
POST    → Create
PUT     → Update
DELETE  → Delete
24. API Response Format

All APIs should follow a consistent response structure.

Success
{
  "success": true,
  "message": "Operation successful",
  "data": {}
}
Error
{
  "success": false,
  "message": "Something went wrong"
}
25. HTTP Status Codes

Use:

200 → Success
201 → Created
400 → Bad Request
401 → Not Authenticated
403 → Not Authorized
404 → Not Found
409 → Conflict
500 → Server Error

Important distinction:

401 = User is not authenticated.

403 = User is authenticated but does not have permission.

This distinction is especially important for:

Study Groups
Group Roles
Protected Documents
Document Permissions
Admin Operations
26. Database Naming Convention

Use camelCase consistently.

Recommended identifiers:

userId
groupId
taskId
documentId
messageId
sessionId
notificationId
createdBy
updatedBy
createdAt
updatedAt

Avoid inconsistent alternatives:

user_id
userid
userID
studentId
group_id
groupID
27. Socket.io Convention

StudySphere uses a shared Socket.io connection.

Do NOT create separate socket connections for every feature.

The primary room identifier is:

groupId

Example:

Machine Learning
groupId = 12345

Socket room:

12345

The same group room can support:

Chat
Focus Rooms
Activity
Notifications
Collaborative Notes
Presence
28. Socket Event Naming

Use:

domain:action

Examples:

chat:message
chat:typing

focus:joined
focus:started
focus:paused
focus:completed

notification:new

activity:new

task:created
task:updated

Keep event names consistent across the project.

Do not create random event naming patterns such as:

sendMsg
newMessage123
startTimerNow
29. Frontend API Convention

Use the shared Axios instance.

Do NOT create a separate Axios instance for every feature.

Frontend request flow:

      ↓

      ↓

      ↓

37. Protected Document Security Rules

The protected document system must follow these rules.

Storage

Uploaded documents must be stored in a private cloud-storage location.

Do NOT expose documents through public URLs.

Access

Every document request must verify:

JWT Authentication
        ↓
User Identity
        ↓
Group Membership
        ↓
Role Permission
        ↓
Document Permission
        ↓
Access Granted / Denied
Unauthorized Users

Unauthorized users must receive:

403 Forbidden

and must not receive the document content.

Audit

Important document operations should be recorded:

User
Document
Action
Timestamp

Examples:

Document Viewed
Document Downloaded
Document Permission Changed
Document Uploaded
Document Updated
